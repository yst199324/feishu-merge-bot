## 一、要解决的问题

### 问题一：合并项目重启期间，云效推过来的消息会丢

现状是云效把报文推到合并项目的 `18123` 端口，项目同步处理完（调云效接口查详情、拼卡片、调飞书发卡）才返回。这个过程要几秒，而**重启那 20 秒里端口不在监听，云效的请求会被直接拒绝**，这条合并请求就再也没有卡片，只能靠人去云效翻。

云效官方文档没有承诺投递失败会自动重投，后台只有一个手工「重新投递」按钮。所以这个洞必须自己补。

### 问题二：依赖服务抖动时，卡片会被刷成红色失败卡

合并项目活着，但云效接口或飞书接口临时出问题（网关 502、读超时、返回内容不是预期格式）时，点「确认合并」或「拒绝」会走到失败分支，把卡片整张换成红色失败卡、按钮消失。等服务恢复，那张卡已经废了，只能去云效手工操作。

要的效果是：**只弹一句提示，卡片一个字都不动，服务恢复后还能继续点**。

## 三、明确不做的事

写清楚是为了以后不再反复讨论。

| 不做的方案 | 不做的理由 |
|---|---|
| 把飞书长连接搬到监听服务 | 同一个应用开两条长连接，飞书只把事件投给其中一条且不广播，表现成"有时有反应有时没反应" |
| 定时轮询云效做对账 | 强依赖云效接口；将来换平台要改三处；`repo-ids` 手工维护；拿全量仓库还会把与自己无关的仓库都拖进来，过滤不了审批人 |
| 卡片过期防护（按钮带发卡时间戳） | 保护范围很窄，真正落笔前本来就会重查云效状态，已被合并或关闭的会被拦掉 |
| 用反向代理或网关做落盘缓冲 | 要引入脚本栈（Nginx + Lua 一类），与现有技术栈不一致，排查要跨两套知识 |
| 引入 Redis、消息队列、数据库 | 单机、一天几十条消息，磁盘目录就够了；多一个组件多一个故障点 |
| 用内存队列 + 定时落盘 | 重启还是会丢，而重启不丢正是这次的目的；落盘后目录本身就是队列 |

## 四、总体结构

### 4.1 链路

```
形态一（默认，只部署合并项目）：
  云效 ──POST──▶ 合并项目 :18123 ──▶ 调云效接口 + 发飞书卡片

形态二（两个都部署）：
  云效 ──POST──▶ 监听服务 :18123 ──写文件──▶ queue/pending/
                                                    │
                                       待发线程每 2 秒扫一次
                                                    │
                                                    ▼
                              合并项目 :18601 /internal/yunxiao ──▶ 调云效 + 发卡片
                                                    │
                                          失败（5xx/超时）
                                                    ▼
                                            queue/retry/
                                                    │
                                       重试线程按阶梯重试，阶梯用尽进 queue/dead/
```

### 4.2 职责边界

| | 监听服务 `feishu-merge-relay` | 合并项目 `feishu-merge-bot` |
|---|---|---|
| 负责 | 校验来源、写文件、转发、按阶梯重试、限额与死信 | 全部业务：查云效、拼卡片、发飞书、处理卡片点击 |
| 不负责 | 不解析报文、不调云效、不发卡片、不连飞书 | 不关心队列怎么实现 |
| 需要哪些凭据 | 只有云效 Webhook 的密钥（用来校验推送来源） | 云效令牌、飞书 app-id/secret、群号 |
| 依赖 | web + json | 全部 |
| 内存占用 | 约 20 MB | 约 200 MB |
| 重启频率 | 极低（不跟业务变化） | 每次改代码都要重启 |
| 端口 | 18123，对外 | 18601，不对公网开放 |

### 4.3 为什么内部接口不复用 `/webhook/yunxiao`

三条硬理由：

1. **返回码语义不同。** 云效入口面向云效，只需要 200 / 400 / 403 / 500（异常如实返回 500，见 6.3），不区分"永久失败"和"稍后重试"；内部入口必须给监听服务三态：200 删文件、400 直接进死信、503 进重试队列。一个接口要同时满足两套语义，只能靠加参数区分，反而更难维护。
2. **密钥耦合。** 转发要原样带 `X-Codeup-Token`，两个服务就得同步同一个云效密钥。那个密钥是给云效用的，跟内部通信无关，同步它纯属给自己加维护点。
3. **排查时分不清来源。** 队列投递的和云效直连的混在一条日志里，出问题看不出消息从哪条路来。

多一个 Controller（约 60 行，业务逻辑全复用）换来这三个好处，划算。

## 五、队列设计

### 5.1 目录结构

```
<监听服务工作目录>/
  relay.jar
  application.yml
  queue/
    pending/     待发：收到了还没成功转发出去的
    retry/     重试：转发失败，等着下一次重试的
    dead/      死信：阶梯用尽仍失败，或永久处理不了，不再自动重试
```

默认路径是工作目录下的 `queue/`，可用配置项改。

### 5.2 文件名规则

| 目录 | 文件名 | 举例 |
|---|---|---|
| `pending/` | `{投递编号}_{首次到达毫秒}.json` | `a1b2c3d4-0001_1763604612000.json` |
| `retry/` | `{投递编号}_{首次到达毫秒}_{已试次数}.json` | `a1b2c3d4-0001_1763604612000_3.json` |
| `dead/` | `{投递编号}_{首次到达毫秒}_{进死信时间}_{原因}.json` | `a1b2c3d4-0001_1763604612000_20261120093012_auth.json` |

`dead/` 文件名最后的**原因标记**是为了补发时能筛：`auth`（云效凭据失效）、`bad`（报文或参数问题）、`exhausted`（六次阶梯用尽）、`expired`（超龄）。换完令牌后一句 `ls *_auth_*.json` 就知道该补哪些，见 14.16。

**为什么文件名里要带"首次到达毫秒"**（评审补的，见 14.13）：文件的修改时间在 `retry/` 里被改成了"下次该重试的时刻"，它是一个未来时间，不能再拿来算"这条进来多久了"。而三个队列超限时要删"最早进来的那一条"、待发队列要判超龄，都得知道真正的到达时间。把它写进文件名，判断"谁最老"和判断"什么时候该重试"就彻底分开了，互不干扰。

**投递编号在入队那一刻就确定，之后不再变化。** 这一点很关键：重试时必须带着同一个编号回去，合并项目才能认出"这是同一条消息"，从而挡住重复发卡。如果每次重试都生成新编号，合并项目会当成新消息，重试几次就发几张卡。

**编号只有一个来源：云效请求头 `X-Codeup-Delivery`。不兼容旧头名，也不自己生成。缺了就直接返回 400、写一条错误日志、不落盘、不进队列。**

理由有三条，都是硬约束：

1. **合并项目本来就不认没有编号的报文。** 它的 `/webhook/yunxiao` 第一件事就是取这个头，取不到直接 400。就算监听服务放行了，转发过去也一定失败，进队列纯属白走一趟。
2. **缺这个头几乎从来不是"云效没发"，而是中间的 Nginx / WAF 把没在白名单里声明的请求头滤掉了。** 现有代码里专门写了这条排查提示。这种情况下监听服务若自己算个编号把消息收下，等于把配置故障悄悄绕过——云效后台点「测试」时会显示推送成功，等真实合并请求来了才暴露，检测点刚好错过最该报错的时刻。直接 400 反而能让人第一时间发现网关配置错了。
3. **自己生成编号还会把去重语义搞乱。** 用报文指纹的话，"内容完全相同但确实是两次不同投递"会被合成一条（比如同一个合并请求关掉又重开，某些场景下报文可能一样）；用到达时间的话，重投时编号又变了。两种都有坑，而收益只是"在一个本来就该报错的场景里勉强收下消息"，不值得。

因此整个链路里，编号从云效来、原样写进文件名、原样通过 `X-Codeup-Delivery` 转发给合并项目，中间**没有任何生成环节**。

**入队前必须查重，且要查两个目录**（评审补的，见 14.14）：写文件之前，先看 `pending/` 和 `retry/` 里有没有同一个投递编号的文件，有就直接返回 200、不落盘。只查 `pending/` 不够——文件一旦失败移进 `retry/`，云效这时重投同一份报文，`pending/` 里已经没有它了，会再写一份新文件，两个并存就会重复处理。`dead/` 里的同编号文件按"已放弃"处理，也直接返回 200，不再复活。

**文件名必须清洗。** 编号来自请求头，属于外部输入，不能直接拼进路径。规则：只保留字母、数字、短横线、下划线，其余一律替换成短横线，长度截到 64 位。这一条是防目录穿越（`../../` 之类）的唯一防线。

### 5.3 到期时间存在哪

**到期时间存在文件的修改时间上，不写进文件内容；首次到达时间存在文件名里。** 两者分工不同，别混用。

- `pending/` 里文件的修改时间 = 到达时间，只用来排队
- `retry/` 里文件的修改时间 = 下次该重试的时刻，只用来判断"到期了没有"
- `dead/` 里文件的修改时间 = 移进死信的时刻（**移入时必须重置成当前时间**，不能把 `retry/` 那个未来时间带过去，否则死信目录限额清理会删错文件）
- `pending/` 和 `retry/` 里，判断"谁最老""是否超龄"一律看文件名里的**首次到达毫秒**（跨队列共用，搬目录不清零）
- `dead/` 里已经没有"还要等多久"的概念，判断保留期和限额清理看文件名里的**进死信时间**（移入时一并重置修改时间为当前）

这样每轮扫描只需要"列目录 + 比较时间"，不用读那几十个文件的内容，开销接近零。同时也自动解决了"重启后补发"：文件本来就在磁盘上，起来后第一轮扫描自然会看到。

### 5.4 上限、超龄、丢弃

| 队列 | 上限（默认） | 超龄（默认） | 超限时 | 超龄时 |
|---|---|---|---|---|
| `pending/` | 50 | 3 小时（从首次到达算） | 删首次到达时间最早的一个，记警告日志 | 移进 `dead/`，记警告日志 |
| `retry/` | 50 | 3 小时（同一个阈值，跨队列累计） | 删首次到达时间最早的一个，记警告日志 | 移进 `dead/`，记警告日志 |
| `dead/` | 500 条 | 7 天（按进死信时间） | 删最早进死信的一个，记警告日志 | **直接删除文件**，记警告日志 |

几条说明：

- **超龄按首次到达时间统一算，两个队列共用同一个阈值**（Q3 定案）：消息不管躺在 `pending/` 还是 `retry/`，年龄都是从"云效推过来那一刻"起算，搬一次队列不清零。这样最坏也在 3 小时内收口，不会出现"待发待 2 小时、再重试 2 小时、最后发出一张废卡"。
- **阈值必须是 3 小时，不能是 2 小时**：重试阶梯累计 2 小时 38 分，若超龄设 2 小时，消息在第 6 次重试（2h37m）之前就已经被判超龄进死信，**最后一档重试永远跑不到**，等于白配。3 小时 = 2h38m + 22 分钟余量。改阶梯时这个值要跟着检查，配置注释里写明这条约束。
- **超龄为什么要有**：合并项目停机几小时后，积压里的请求多半早被人处理掉了，再发卡片只会刷屏。有 14.1 的状态复查和每轮限速兜着，超龄是第三道。
- **"删最早"必须按文件名里的首次到达时间，不能按修改时间**：`retry/` 的修改时间是"下次该重试的时刻"（未来），按它删会删掉最快该重试的那条，而不是最老的那条。这是评审时发现并修正的一处逻辑错误（见 14.13）。
- **`dead/` 也要按时间清理，不能只靠 500 条上限**（评审补的）：一天只失败一两条的话，500 条要攒一年多，期间报文（含姓名、邮箱）会一直躺在磁盘上。7 天保留期给人工补发留了足够窗口，过期直接删文件。清理按文件名里的"进死信时间"判断，不用修改时间。
- **丢弃必须记日志**：日志里要有编号、文件大小、丢弃原因。没有这行日志，"消息不见了"就永远查不出来。

### 5.5 重试阶梯

| 第几次重试 | 距上次失败的等待 | 累计经过时间 | 打算覆盖什么 |
|---|---|---|---|
| 1 | 5 秒 | 5 秒 | 单次网络抖动、连接池瞬时打满 |
| 2 | 30 秒 | 35 秒 | 合并项目重启（约 20 秒起停） |
| 3 | 2 分钟 | 2 分 35 秒 | 云效接口短时 5xx、网关切节点 |
| 4 | 5 分钟 | 7 分 35 秒 | 云效侧持续抖动、发版窗口 |
| 5 | 30 分钟 | 37 分 35 秒 | 需要人工介入才能恢复的故障 |
| 6 | 2 小时 | 2 小时 37 分 35 秒 | 人不在（午休、开会、夜里），回来修好后还能补上 |

六次全失败 → 移进 `dead/`，记错误日志。**阶梯写成一个列表，列表有几个条目就是重试几次**，加一条就多一次，不用改代码逻辑。

几点说明：

- **为什么第一步还留 5 秒**：合并项目重启要 20 秒左右，5 秒这一次注定失败，看着像浪费。但另一种更常见的故障是云效或飞书接口一次瞬时超时，5 秒就能救回来，用户少等 25 秒。这一次失败的成本只是一次连接被拒，可以忽略，所以留着。
- **为什么不做随机抖动**：抖动是为了避免大量任务在同一瞬间一起重试、把下游压垮。这里重试线程固定 1 个、严格串行处理，最多 50 条，不存在并发冲击，加了反而让等待时间不可预测，排查时看不出规律。
- **为什么单次间隔不设上限但又不能太长**：最后一步 2 小时，是为了"晚上挂掉、第二天早上才修"这种场景还能补一张卡。再往后加（比如 6 小时）收益很小——到那时合并请求基本都被人手工处理掉了，而发卡前还有一道状态复查（见 14.1）会把它们拦掉，加长只是让文件在 `retry/` 里多躺几小时。

### 5.6 扫描节奏与线程数

消费侧一共两组线程，互相独立：

| 组 | 线程数 | 干什么 | 每轮最多处理 |
|---|---|---|---|
| 待发组 | 默认 1 个，可配置调大 | 扫 `pending/`，转发成功的删文件，失败移进 `retry/` | 10 条 |
| 重试组 | 固定 1 个 | 扫 `retry/` 里到期的文件，成功删文件，再失败次数加一、改时间，阶梯用尽进 `dead/` | 5 条 |

两组都是每 2 秒扫一次，启动时立刻先跑一轮。

**让路规则**：`pending/` 里积压超过 10 个时，重试组本轮直接跳过，把云效和飞书的调用额度全留给新消息。

⚠️ 这个阈值必须**小于待发队列上限**。上限从 1000 下调到 50 之后，如果让路阈值还留着 50，`pending/` 永远不可能"超过 50 个"，这条规则就形同虚设。默认给 10，可配置。

**转发线程调大的影响**：待发组配成多个线程后，就是几条并行转发，不再严格串行。这时"后到的先发卡"是可能的。实际影响很小——每条消息发卡前都会重查一次云效状态，不会因为顺序变化发错卡。真要保证顺序，就保持默认的 1。

### 5.7 顺序

待发组可以保序的前提是**只跑 1 个线程**，并且按文件的修改时间从早到晚处理（不依赖文件名排序，目录列表的返回顺序在不同文件系统上并不一致）。

重试组始终只有 1 个线程，天然保序。

### 5.8 成功之后怎么收尾

两种队列的收尾方式不一样，别搞混：

- `pending/` 转发成功 → **删文件**
- `retry/` 重试成功 → **删文件**（不回 `pending/`，避免来回搬）
- 两者失败 → 都往 `retry/` 挪，文件名带上新的次数、修改时间改成下次该试的时刻

删文件时如果进程正好崩溃，重启后会再转发一次。合并项目按投递编号去重，第二次通常返回 200，然后正常删掉、不会重复发卡。万一去重记录已经过期，最多多出一张相同的审批卡，不影响合并结果（见 14.12，Q1 已决定不为这个改代码）。这是"先删还是先记"这类顺序问题不用纠结的原因。

**手工补发的正确姿势**（评审补的）：从 `dead/` 或 `retry/` 里挑一条要补发时，不能直接 `mv` 回 `pending/`。要做三件事：文件名改成 `pending/` 的格式（`{编号}_{新的到达毫秒}.json`，去掉次数和原因标记）、把已试次数归零、修改时间设为当前时间。否则从 `retry/` 搬回来的文件带着 `_6`，第一次失败就会立刻又进死信，等于补发永远不成功。**这一步由 `requeue-dead.sh` 完成，批量补发办法见 14.16。**

## 六、接口契约

### 6.1 云效 → 监听服务

```
POST http://<服务器IP>:18123/webhook/yunxiao
请求头：X-Codeup-Token、X-Codeup-Delivery、X-Codeup-Event
请求体：云效报文原文（字节原样）
```

| 情况 | 返回 | 说明 |
|---|---|---|
| 密钥不匹配 | 403 | 立即拒绝，不落盘 |
| **缺 `X-Codeup-Delivery`** | **400** | **写错误日志（把请求头全量打出来，脱敏后），不落盘、不进队列。** 多半是网关把未声明的请求头滤掉了，见 5.2 |
| 报文超过 2 MB | 413 | 记错误日志，不落盘 |
| 写文件失败（磁盘满、权限错） | 500 | **必须返回失败**，不能假装成功 |
| 同一编号已在 `pending/` 或 `retry/` | 200 | 重复投递，跳过落盘 |
| 正常 | 200 | 写完文件才返回，写完即算收下 |

关于磁盘写满时返回 500 这件事：这是唯一正确的行为，不能假装成功——假装成功的后果是云效以为送达、我们其实没存下来，消息彻底消失。返回 500 之后云效后台会显示这条投递失败，需要人工去点「重新投递」补回来（云效不会自动重试）。手册里要写这个处置动作。

### 6.2 监听服务 → 合并项目

```
POST http://<合并项目地址>:18601/internal/yunxiao
必带请求头：
  X-Codeup-Delivery = 入队时固化的投递编号   ← 必须叫这个名字
  Content-Type      = 原样透传云效那一次请求的 Content-Type（含 charset）
建议一并透传：
  X-Codeup-Event（合并项目日志里要打事件名）、X-Relay-From（标记来源，便于排查）
不要带：X-Codeup-Token（内部入口不验签，带了等于把云效密钥抄给内部链路）
请求体：报文原文（字节原样透传，不做任何重新序列化）
读超时：30 秒
```

⚠️ **`X-Codeup-Delivery` 这个头名不能改。** 合并项目的 `WebhookGuard.deliveryOf()` 认 `X-Codeup-Delivery`（另有一个历史兼容头），取不到就返回 400。之前文档写过"转发时带 `X-Relay-Delivery`"，那样每条消息都会因为缺编号被判永久失败、直接进死信——这是评审时发现的最严重一处错误。`X-Relay-Delivery` 如果要留，只能作为附加标记，不能替代它。监听服务缺这个头时直接 400，不存在"自己补一个编号"的情况（见 5.2）。

⚠️ **Content-Type 不要写死成 `application/json`。** 合并项目用 `@RequestBody String` 接报文，解码字符集受请求头里的 `charset` 影响；云效直连时一切正常，是因为云效带了正确的字符集。转发时若写死不带 `charset`，中文标题、提交说明可能变乱码，而且只有走监听服务这一条路会出问题，很难联想到是转发层的锅。原样透传即可。

**必须原样透传请求体**：一旦重新序列化，字段顺序、空值处理都会变，合并项目那边解析出来的东西未必一样。

返回码三态，监听服务只看这个：

| 返回码 | 什么时候返回 | 监听服务动作 |
|---|---|---|
| **200** | 已发卡；或确认是重复投递；或不是合并请求事件（如"测试"按钮发的推送事件） | 删文件，处理结束 |
| **400** | **重试再多次也没用**：报文解析不了、取不到仓库号或合并请求号、缺投递编号、**云效令牌 401 / 403** | 直接进 `dead/`，不浪费重试 |
| **503** | 现在处理不了：云效接口连不上或返回 5xx、飞书发卡失败、其他未预期异常 | 进 `retry/`，按阶梯重试 |
| **500** | 未预期的异常 | 同 503 |
| **404 / 405** | **内部入口没开或路径写错**（开关默认 `false`，接口压根不注册） | **直接进 `dead/`，不重试**，并打一条 ERROR：「合并项目内部入口调不通，请检查 INTERNAL_ENDPOINT 是否为 true、端口是否正确」，见 14.8 |
| 连不上、读超时 | —— | 同 503 |

**400 / 404 / 503 的判定要用白名单，不要用异常类别去猜。** 400 只给"重试再多次也没用"的情况，**其余所有异常一律 503**——但 404/405 和"连不上"要先挑出来单独处理，理由见下。发飞书卡片失败抛的是 `IllegalStateException`，不是云效调用层的 `YunxiaoException`，第七节那套异常分类覆盖不到它；按类别判断会把它落到"其他"，可能误判成 400 直接丢掉，而它其实重试一次就好了。

⚠️ **为什么 404 必须单独归类**：内部入口开关默认关着，接口不注册时返回 404。如果 `RelayClient` 只按"200 成功、400 死信、其余重试"来分，404 会落进"可重试"，于是每条消息都白等六次、跨 2 小时 38 分，最后全进死信——这正是"开关没开、监听服务一直调不通"最典型的翻车现场，而且日志里只写着"转发失败"，看不出根因。单独判 404 之后，第一条消息就能给出准确提示。

**凭据问题（401/403）确定归 400，直接进 `dead/`**（Q2 定案）。令牌不会自己变好，走 503 就是白等六次、白占 50 条重试队列。代价是令牌修好后这些消息不会自动重发，所以有两条配套要求：

1. 内部入口在返回 400 前，日志必须**单独打一行**「云效凭据失效，请更换 x-yunxiao-token 后手工补发」，不能混在"报文解析失败"里，否则运维看不出根因。
2. 进死信时文件名带上原因标记（见 14.16），补发时能一眼筛出"这批是换完令牌就该补的"。

注意 400 的语义因此从"报文有问题"扩成"**重试无用、需要人工介入**"，文档和代码注释都按这个口径写。

### 6.3 云效直连 → 合并项目

`POST /webhook/yunxiao` 的请求结构、来源校验、事件过滤、返回 200/400/403 全部保持现状。**唯一改动**：处理异常时不再吞掉异常返回 200，改成如实返回 500（R13，用户已确认）。

理由：吞异常回 200 会让云效后台显示"投递成功"，但卡片其实没发出去，运维完全看不出丢了一条。返回 500 后云效后台会显示投递失败，人能看见，也才有机会去点「重新投递」。这个改动对直连形态和走监听服务的形态都是对的。

内部入口与它的区别只在两点：不做来源校验、失败要区分 400（永久）与 503（可重试）。两者共用同一份业务处理逻辑。

### 6.4 内部入口的访问控制

不做代码里的来源校验，理由：将来两个服务可能不在同一台机器，写死本机地址会让分机器时要改代码。改用网络层控制：

- 合并项目监听 `0.0.0.0:18601`，**不绑定 127.0.0.1**
- 云服务器安全组（或本机防火墙）**不放行 18601**
- 将来分机器部署，只需在安全组里放行"监听服务那台机器的 IP 访问 18601"，代码和配置都不用动

风险与缓解写在第十三节。

## 七、卡片容错设计

### 7.1 现状：四个按钮各自的行为

| 点击的按钮 | 第一步做什么 | 云效抖动时现在会怎样 |
|---|---|---|
| 合并 | 先查一次详情，再弹确认卡 | 异常冒到最外层兜底，只弹提示、**不换卡** ✅，但提示是"处理失败：连接被拒"这类原始报错 |
| 取消 | 先查一次详情，再换回待审批卡 | 同上，卡片不变 ✅ |
| 确认合并 | 加锁 → 查详情 → 调合并接口 → 确认状态 | 走失败分支，**换成红色失败卡，按钮消失** ❌ |
| 拒绝 | 加锁 → 查详情 → 调关闭接口 | 同上 ❌ |

所以这次改动不是"从零加功能"，是**把四条路径的出口统一**，并把"确定没执行"和"结果未知"分开对待。

### 7.2 异常分类

现在判断"令牌问题"靠字符串里找 `HTTP 401`，属于能跑但不好维护。改成给异常带一个类别：

| 类别 | 判定依据 | 典型场景 |
|---|---|---|
| 服务不可用 | 连接被拒、读超时、DNS 失败、HTTP 502/503/504、返回内容不是能被解析的 JSON | 云效挂了、网关挂了 |
| 令牌问题 | HTTP 401、403 | 令牌过期、权限被改 |
| 其他 | 其余状态码、业务拒绝 | 冲突、卡点未过 |

判定放在云效调用层所有抛出 `YunxiaoException` 的地方——全项目只有那里能拿到状态码和异常类型，别处只能靠猜。实际有六处：两处 `HttpStatusCodeException`（能拿到状态码）、`RestClientException`（网络与超时）、`unwrap()` 里的"云效返回失败"和"返回内容无法解析"、以及参数校验失败。顺手把现有的字符串匹配（`msg.contains("HTTP 401")`）删掉。

注意这套分类**只覆盖云效调用**。发飞书卡片失败抛的是 `IllegalStateException`，不在其中；内部入口因此不能靠类别判断 400/503，规则见 6.2。

### 7.3 统一出口

新增一个出口，只做四件事：

1. 写审计记录（结果记"未执行"）
2. 弹一行提示：`云效暂时联系不上，这次没有执行，稍等一会儿再点`
3. **不碰卡片**（不调用换卡逻辑，飞书就会保留原卡片）
4. 撤掉幂等名额（否则要等 60 秒或 30 分钟才能再点）

关于第 4 条：`doMerge` / `doClose` 的 catch 里**已经**在调用 `idempotent.forget(idemKey)`，且"确认合并结果"那一步刻意不撤销。统一出口在这两条路径上不要重复加，只需保证换掉 `fail()` 时不把已有的 `forget` 一起删掉。真正需要补 `forget` 的是"点合并 / 点取消"这两个落到最外层兜底的路径。

### 7.4 接进五个落点

| 落点 | 现在的行为 | 改成 |
|---|---|---|
| 点「合并」查详情失败，冒到最外层兜底 | 弹原始报错 | 判定为服务不可用时，弹上面那句提示 |
| 点「取消」查详情失败，同上 | 同上 | 同上 |
| 「确认合并」的查详情阶段失败 | 换红色失败卡 | 走统一出口，不换卡 |
| 「拒绝」的查详情阶段失败 | 换红色失败卡 | 走统一出口，不换卡 |
| 重复点击分支里重查详情失败 | 把卡片重画成待审批卡（字段会是空的） | 走统一出口，不换卡 |

### 7.5 必须守住的安全边界

**只有"确定什么都没发生"时，才允许不换卡。**

有一处例外必须保留原行为：「合并接口已经返回成功，但确认状态时出错」。这时候合并可能真的成功了，如果也"不换卡、让你再点"，就会重复合并。这个分支必须换卡、必须提示"请去云效确认是否已合并"、必须保留幂等登记。

规则写进代码注释：

> 只要调用过写接口（合并、关闭），结果未知就必须换卡并撤掉按钮，不能走"不换卡可重试"这条路。

### 7.6 合并项目整个进程挂掉

长连接跟着断，点按钮时飞书客户端弹它自己的提示（文案在飞书客户端里，我们改不了）。卡片不变，服务起来后照样能点。

这条需求已经满足，不做额外开发。本次的卡片改动覆盖的是"合并项目活着、依赖服务抖动"这个日常更常见的场景。

## 八、配置项清单

### 8.1 监听服务（新建，全部配置项）

**和合并项目用同一套 `.env` 机制**（评审补的，见 8.3）：这份 `application.yml` 进仓库、里面只有占位值，真实值放同目录的 `.env`（不进库）。这样监听服务的 yml 也能整份覆盖到服务器，不用每次改完再手工合并配置。

```yaml
spring:
  config:
    # 把工作目录下的 .env 按 properties 格式读进来。
    # [.properties] 不能省（.env 没有扩展名，Spring 猜不出解析器）；
    # optional: 不能省（文件缺失时回落默认值，不报错）
    import: optional:file:./.env[.properties]

server:
  port: ${RELAY_SERVER_PORT:18123}

relay:
  # 云效 Webhook 的 Secret Token，必须和云效后台填的一致。真实值放 .env
  webhook-token: "${YUNXIAO_WEBHOOK_TOKEN:在这里填云效后台的密钥}"

  # 报文最大字节数，超过直接拒绝（防止超大报文写满磁盘）
  max-payload-bytes: 2097152        # 2 MB

  # 队列根目录，下面会自动建 pending/retry/dead 三个子目录
  queue-dir: ${RELAY_QUEUE_DIR:./queue}

  # 扫描间隔（毫秒）
  scan-interval-ms: 2000

  # 消息总寿命：从"云效推过来那一刻"算起，pending/ 和 retry/ 共用同一个阈值。
  # ⚠️ 必须大于重试阶梯累计时长（5+30+120+300+1800+7200 = 9455 秒 ≈ 2h38m），
  #    否则最后一档 2 小时重试还没跑到，消息就已经被判超龄进死信了。
  #    改 delay-seconds 时务必回来检查这个值。
  max-age-minutes: ${RELAY_MAX_AGE_MINUTES:180}    # 3 小时

  # 待发队列
  pending:
    max-size: ${RELAY_PENDING_MAX_SIZE:50}
    batch-per-round: 10             # 每轮最多处理几条

  # 重试队列
  retry:
    max-size: ${RELAY_RETRY_MAX_SIZE:50}
    batch-per-round: 5
    max-pending-before-yield: 10    # 待发积压超过这个数，重试线程本轮跳过；必须小于 pending.max-size
    # 每个条目是一次重试前的等待秒数，条目数 = 重试次数
    # 5 秒 → 30 秒 → 2 分 → 5 分 → 30 分 → 2 小时
    delay-seconds: [5, 30, 120, 300, 1800, 7200]

  # 死信目录
  dead:
    max-size: 500
    max-age-days: ${RELAY_DEAD_MAX_AGE_DAYS:7}   # 按进死信时间清，过期直接删文件

  # 转发目标（合并项目的内部入口）
  target:
    url: "${RELAY_TARGET_URL:http://127.0.0.1:18601/internal/yunxiao}"
    connect-timeout-ms: 3000
    read-timeout-ms: 30000          # 合并项目同步处理要几秒，这里必须留足
    threads: 1                      # 待发组线程数，默认 1（保序）；消息量大时调大，调大后不保序
```

```yaml
mergebot:
  # 内部入口开关（Q5 定案：保留，默认 false）。
  # 只部署合并项目时关掉，接口不注册；部署监听服务时在 .env 里设 true
  # 忘了打开的自检办法见 14.8

```

### 8.3 监听服务的 `.env`（评审补的）

可以，也应该支持——**和合并项目用完全一样的一套**，运维不用记两套规则。

| 文件 | 进不进仓库 | 内容 |
|---|---|---|
| `application.yml` | 进 | 只有 `${KEY:占位}`，可整份覆盖到服务器 |
| `.env.example` | 进 | 键名齐全、值留占位，告诉别人要配什么 |
| `.env` | **不进**，加进 `.gitignore` | 本机真实值，权限 `600` |

`.env` 里至少这几项（两个服务各一份，别混用）：

```
RELAY_SERVER_PORT=18123
YUNXIAO_WEBHOOK_TOKEN=云效后台那个密钥
RELAY_TARGET_URL=http://127.0.0.1:18601/internal/yunxiao
RELAY_QUEUE_DIR=./queue
```

三个必须注意的点，都是现有项目踩过的：

1. **启动脚本里要 `cd` 到 jar 所在目录**。`./.env` 是相对**进程工作目录**的，从别处 `java -jar /opt/relay/relay.jar` 起，会读不到 `.env`；又因为写了 `optional:`，找不到是**静默跳过**、不报错，表现成"启动正常但密钥是占位值"。合并项目的 `deploy/start.sh` 已经有 `cd "$APP_HOME"`，照抄即可，并在缺 `.env` 时打一行提示。
2. **外置 `application.yml` 的优先级高于 `.env`**。所以服务器那份 yml 必须也写 `${KEY:占位}`，不能写死字面值，否则会把 `.env` 盖掉。合并项目上一轮就是为这个改的。
3. **两个服务的 `YUNXIAO_WEBHOOK_TOKEN` 填同一个值**：监听服务要用它验云效的签名，合并项目留着 `/webhook/yunxiao` 作应急直连通道也用它验签。填成一样，云效地址改到哪一边都能通过，切换时不用改密钥。这和 4.3 里"转发不带 `X-Codeup-Token`"不冲突——那是说内部链路上不传这个密钥，不是两边配置不能一样。

## 十、部署与切换

### 10.1 形态一：只部署合并项目（默认）

云效地址填 `http://<服务器IP>:18123/webhook/yunxiao`，行为与现在完全一致。`internal-endpoint-enabled` 保持 `false`。

### 10.2 形态二：两个都部署

步骤：

1. 停合并项目
2. 合并项目 `.env` 增加 `SERVER_PORT=18601`、`INTERNAL_ENDPOINT=true`。**`INTERNAL_ENDPOINT=true` 这一行最容易漏**，漏了的表现是监听服务一直转发失败，排查办法见 14.8
3. **确认合并项目的 `server.address` 保持注释状态**，不要写成 `127.0.0.1`。写成 127.0.0.1 本机现在能用，但将来两个服务分机器部署时，监听服务就连不过来了，届时得改配置重启
4. 启动合并项目，用 `curl` 打一次内部入口确认返回码正常（见 12.3）。**顺手做一次上线自检**：临时把 `TEST_ENDPOINTS=true` 打开并重启，在服务器本机用 `127.0.0.1` 调一次 `/test/doctor`，确认「内部入口开关」那一项是通过，然后立刻改回 `false` 再重启（这个开关平时必须关着，见 14.8）
5. 部署监听服务到**独立目录**：`relay.jar`、`application.yml`、`start.sh`、`stop.sh`、`restart.sh`、`requeue-dead.sh`、`start.bat`（可选）。三个启停脚本从合并项目 `deploy/` 复制改参数（差异清单见 14.9），`chmod +x *.sh`
6. 把 `.env.example` 复制成 `.env`，填 `YUNXIAO_WEBHOOK_TOKEN`、`RELAY_TARGET_URL` 等真实值，`chmod 600 .env`。确认 `start.sh` 里已经 `cd` 到这个目录（见 8.3，工作目录不对会静默读不到 `.env`）
7. 用 `./start.sh` 启动监听服务，确认：`18123` 在监听、`18601` 从外网访问不通、`queue/` 三个子目录已自动建好且权限 700、**启动日志里目标探测那一行是「内部入口可达」而不是 404 的 ERROR**
8. 云效后台把 Webhook 地址改成指向 `18123` 的地址（**只改端口那一处**）
9. 在云效后台点一次「测试」，看监听服务日志里有没有落盘记录

两条不用纠结的事：

- **启动顺序无所谓。** 先起监听服务也行，这时候转发会因为连不上而进 `retry/`，等合并项目起来自动补发。
- **两边 `.env` 里的 `YUNXIAO_WEBHOOK_TOKEN` 填同一个值**（合并项目那边的键名是 `YUNXIAO_WEBHOOK_TOKEN`，见 8.3）。监听服务要用它验签；合并项目留着 `/webhook/yunxiao` 作为应急直连通道，也用它验签。填成一样，云效地址改到哪一边都能通过，切换时不用改密钥。

### 10.3 回滚（形态二 → 形态一）

1. 停监听服务
2. 云效后台把地址改回 `18123` 直连合并项目
3. 合并项目 `.env` 改回 `SERVER_PORT=18123`、`INTERNAL_ENDPOINT=false`
4. 重启合并项目

⚠️ **回滚前必须先清空队列，否则积压的消息会直接丢掉。** 上面第 1 步停掉监听服务后，`pending/` 和 `retry/` 里剩下的文件不会再有人消费，云效也不会重投它们。原文档写"残留文件不影响运行（只是不再被消费）"，这句话把"消息丢了"说得像没事一样，是评审时纠正的一处遗漏。正确做法二选一：

- **推荐**：先别停监听服务。把云效地址改回直连，等监听服务把队列里剩下的都转发完（看 `/health` 条数归零），再停它。
- 来不及等：把 `pending/`、`retry/` 里的文件逐个用 `curl` 打到合并项目的 `/webhook/yunxiao`，带上 `X-Codeup-Token` 和 `X-Codeup-Delivery`（值取文件名里的编号），确认返回 200 后删文件。

`dead/` 里的文件不受上面两步影响，本来就要人工处理，补发办法见 14.16（`requeue-dead.sh`，7 天内可补）。

### 10.4 两种形态的端口对照

| | 形态一 | 形态二 |
|---|---|---|
| 云效指向 | 合并项目 18123 | 监听服务 18123 |
| 合并项目端口 | 18123 | 18601（不对公网） |
| 监听服务 | 不存在 | 18123（对外） |
| 需要改云效后台 | 不需要 | 改端口 |

## 十一、实施顺序

按这个顺序，每一步都能单独验证，不会出现"改完一堆不知道哪坏了"：

1. **合并项目：异常分类。** 改完可以用一个不存在的云效地址验证，看日志里是不是"服务不可用"。
2. **合并项目：抽出 `WebhookDispatchService` + 内部入口 + 返回码三态。** 打开内部入口开关，用 `curl` 打这个接口，看 200 / 400 / 503 是否按预期返回；再关掉开关，确认返 404、日志能指出是开关没开。
3. **合并项目：卡片容错 + 发卡前状态复查 + doctor 自检项。** 把云效地址改错，逐个点四个按钮，确认卡片都不变、提示都能看懂；`INTERNAL_ENDPOINT` 关着时 doctor 那一项报失败。
4. **监听服务：队列与两个线程。** 手工往 `pending/` 丢一个报文文件，看会不会被转发、失败会不会进 `retry/`、阶梯用尽后会不会进 `dead/`；404 要直接进死信、不重试。
5. **监听服务：接收接口、限额、启动探测、`/health`。** 把 `pending.max-size` 临时改成 5，用 `curl` 灌 6 条，看最旧的一条是否被删、日志里有没有丢弃记录。测完改回 50。再验开关关着时启动日志会报 404 的 ERROR。
6. **联调：** 云效端口切过去，制造一次合并请求，观察从推送到卡片出现的全链路。
7. **部署脚本与手册：** `start.sh` / `stop.sh` / `restart.sh` / `requeue-dead.sh`、两份 `.env.example`、手册三节。按 12.4 的 E1~E6 逐条验，重点确认两个服务的启停互不干扰。

| E2 | 再执行一次 `./start.sh` | 提示"已经在运行，PID=xxx"并退出，**不会起第二个进程** |
| E3 | `./stop.sh` | 先 SIGTERM、正常退出后删掉 `relay.pid`；**合并项目进程不受影响**（`ps -ef \| grep merge-bot.jar` 还在） |
| E4 | `./restart.sh` | 先停后起，中间等 2 秒；`restart.sh` 自己不实现 kill 逻辑，只调另外两个脚本 |
| E5 | 在合并项目目录执行 `./restart.sh` | **监听服务进程不受影响**（两边 jar 名、pid 文件、日志目录完全不同，见 14.9） |
| E6 | 故意把 `relay.pid` 删掉再执行 `./stop.sh` | `pgrep -f relay.jar` 兜底仍能找到并停掉进程 |

## 十四、补充的设计点（原需求里没提，但必须有）

这一节是评审时补出来的，每一条都对应一个真实会踩的坑。

### 14.1 发卡前必须重查状态，只给"待合并"的发卡

**不做会怎样**：合并项目停机三小时，积压 40 条，恢复后全部发卡。这 40 个请求里大部分早被人处理掉了（已合并、已拒绝关闭、被撤回），群里瞬间出现 40 张已经没用的卡，比丢消息还难受。

**做法**：合并项目在发卡前本来就要查一次云效详情，加一句判断——**只给状态是"待合并"的发卡**，其余状态一律不发，返回 200（相当于"这条不需要处理了"），记一条 info 日志。

用白名单（只认"待合并"）而不是黑名单（排除已合并、已关闭），因为云效将来可能新增状态，白名单自动覆盖，黑名单会漏。云效详情接口目前的状态就三种：`TO_BE_MERGED`（待合并）、`MERGED`（已合并）、`CLOSED`（已关闭/已拒绝），判断条件可以直接用现有的 `mr.mergeable()`，它本身就是"状态等于待合并"。

**但必须加一条兜底，否则会出比多发卡严重得多的事故**：

> 只有"明确拿到了状态、且状态不是待合并"才跳过。**状态为空或取不到，照常发卡。**

原因：这个项目在字段映射上踩过坑（新版报文把 `iid` 改成 `local_id`、仓库 ID 换了位置）。如果哪天云效详情接口的状态字段也变了，白名单会把"读不到状态"当成"不是待合并"，结果是**所有卡片静默不发，日志里还写着"状态不是待合并，已跳过"，看起来完全正常**。这种故障比丢一张卡难查十倍——群里的表现是"机器人彻底不工作了"，日志却一天下来一条错误都没有。

宁可多发一张卡（多一张废卡，人一眼就能看出来），也不要静默全停。

**影响范围**：这个判断只在"积压回放"时起作用。实时收到的 `open` / `reopen` 事件，那一刻状态几乎必然是待合并，加了判断也不会少发。所以它不会影响日常，只在停机恢复时拦住废卡。

### 14.2 投递编号在入队时固化

**不做会怎样**：每次重试生成新编号，合并项目认不出这是同一条，重试三次就发三张卡。

**做法**：入队时确定编号并写进文件名，转发时写进 `X-Codeup-Delivery` 头（头名不能改，原因见 6.2）。

### 14.3 文件名清洗

**不做会怎样**：编号来自请求头，恶意构造 `X-Codeup-Delivery: ../../etc/passwd` 就能往任意路径写文件。

**做法**：只保留字母、数字、短横线、下划线，长度截断到 64 位。

### 14.4 报文大小上限

**不做会怎样**：有人或某个异常客户端 POST 一个几百 MB 的报文，磁盘瞬间被占满。

**做法**：超过 2 MB 直接返回 413，不落盘，记错误日志。

### 14.5 文件与目录权限

**不做会怎样**：报文里有提交人姓名、邮箱、提交说明，默认权限是所有人可读。

**做法**：目录 `700`、文件 `600`，由监听服务启动时设置并检查。

### 14.6 转发超时要留足

**不做会怎样**：合并项目同步处理一条要几秒（调两三次云效接口 + 一次飞书接口），如果读超时设成 5 秒，会出现"合并项目其实成功了，监听服务却判成失败"→ 重试 → 重复发卡。

**做法**：读超时 30 秒。另外合并项目那边的处理耗时如果可能超过 30 秒（比如云效接口特别慢），要么调大这个值，要么接受"它其实成功了、我们判成失败"。后者会触发一次重复转发，被去重挡住则没事，挡不住最多群里多一张卡（见 14.12），不影响合并结果。

### 14.7 待发积压时重试线程让路

**不做会怎样**：云端恢复瞬间，重试线程和待发线程同时抢接口额度，新消息被老消息挤在后面。

**做法**：待发积压超过 10 条时，重试线程本轮直接跳过。这个阈值必须小于待发队列上限（50），否则规则永远不触发。

### 14.8 自检要能一眼看出"内部入口开关没开"

**不做会怎样**：开关默认 `false`，部署形态二时忘了在 `.env` 里打开，监听服务会一直转发失败。而失败日志长得和网络抖动一模一样，排查方向会被带到"网络、防火墙、端口"上去，绕一大圈才发现是配置漏了一行。

**做法分三层，被动和主动都要有**：

**① 合并项目 `/test/doctor` 加一项「内部入口开关」**（你提的这条）。直接读 `mergebot.internal-endpoint-enabled`，**只报事实、不猜部署形态**——合并项目根本无从知道监听服务有没有部署：

| 状态 | 结论 |
|---|---|
| `true` | 通过：「内部入口已开启，监听服务可以转发过来」 |
| `false` | **警告**：「内部入口未开启。只部署合并项目时这是对的；若已部署监听服务，转发会一直失败，请在 `.env` 设 `INTERNAL_ENDPOINT=true` 并重启」 |

真正能确定"形态二 + 开关没开"的是监听服务那一侧（它存在本身就说明是形态二），由下面的 ② ③ 判定。doctor 这一项的价值是让人上线验收时**看见这个开关的当前值**，别让它藏在 `.env` 里没人注意。

⚠️ **这项自检有个绕不开的局限，必须写进手册**：`SelfCheckService` 和 `TestController` 整个类都挂着 `@ConditionalOnProperty(name = "mergebot.test-endpoints", havingValue = "true")`，而服务器为了安全通常把 `TEST_ENDPOINTS=false` 关着——**也就是说 doctor 在生产上根本打不开**。所以这项的定位是"**上线验收用**"：部署形态二时临时把开关设成 `true`，在服务器本机用 `127.0.0.1` 跑一次 doctor，确认通过后立刻改回 `false` 并重启。它不能当作运行时的自动告警。实现上就是往 `items.add(...)` 列表里加一项（现有 `pass/warn/fail/skip` 四种结果可复用），约 15 行。

**② 监听服务启动时主动探测一次目标地址**（补的，比 ① 更有用）。启动完成后立刻对 `target.url` 发一次探测请求（不带业务报文即可），按结果打日志：

- 200 / 400 → INFO「内部入口可达」
- **404 / 405 → ERROR「合并项目内部入口没开，请检查 INTERNAL_ENDPOINT」**
- 连不上 → WARN「合并项目还没起来，等它起来后队列会自动补发」（这个不算故障，启动顺序本来就无所谓）

这样不用等第一条真实消息，启动日志里就能看到结论。约 15 行。

**③ `/health` 加上"最近一次转发结果"和"连续失败次数"**（补的）。`/health` 挂在监听服务自己的 18123 上，不受 `test-endpoints` 开关影响，是生产上真正随时能看的那一个。除了三个目录的条数和最老文件时间，再加：最近一次转发的状态码（或错误类型）、连续失败次数、最后一次成功转发的时间。运维看一眼就知道是"队列空着一切正常"还是"一直调不通、文件在积压"。

配套还有 6.2 那条：**404/405 直接进死信并打明确的 ERROR 日志**，不按网络失败重试六次。这三层合起来，"开关没开"这件事在启动日志、`/health`、消息日志里都能看到，不依赖有人记得去调 doctor。

### 14.9 两个服务各自独立的启停脚本

**不做会怎样**：用同一个脚本管两个进程，重启监听服务时把合并项目也带停。

**做法**：监听服务目录下有一套**完整**的 `start.sh` / `stop.sh` / `restart.sh`，三个脚本各自只做一件事，和合并项目那套 **结构完全一致、参数不同**。直接从 `deploy/` 复制过来改，比新写一套稳（那套已经处理过 pid 文件残留、进程名兜底、优雅关闭超时强杀、端口释放等待这些坑）。

| 脚本 | 职责 | 从合并项目模板复制后要改的地方 |
|---|---|---|
| `start.sh` | 只做启动：`cd` 到 jar 目录 → 前置检查 → `nohup` 后台起 → 等 8 秒验活 → 打印日志与后续命令 | `APP_NAME=relay`、`APP_JAR=relay.jar`、`relay.pid`；JVM 内存降到 `-Xms128m -Xmx256m`（只有 web + 队列，没有飞书 SDK）；验活关键字改成 `Started RelayApplication`；日志目录 `relay/logs/` |
| `stop.sh` | 只做停止：pid 文件 + `pgrep -f` 双路找进程 → `SIGTERM` → 等最多 30 秒 → 超时 `kill -9` | `APP_NAME`、`APP_JAR`、`PID_FILE` 同上；`pgrep -f "$APP_JAR"` 用 `relay.jar`，**不会误匹配到 `merge-bot.jar`** |
| `restart.sh` | 只做编排：调 `stop.sh` → 等 2 秒让端口释放 → 调 `start.sh`，任一失败就停在这里 | 只改脚本头注释里的服务名，逻辑一行不动 |

四个必须守住的点：

1. **`cd "$APP_HOME"` 一定要留着**。8.3 说了，`./.env` 按进程工作目录解析，不切目录会静默读不到 `.env`，表现成"配置改了没生效"。现有模板里这段注释写得很详细，别删。
2. **`--spring.config.additional-location=file:"$APP_HOME"/` 要留着**，外置 `application.yml` 靠它加载。
3. **两个服务必须部署在不同目录**，各自的 `application.yml`、`.env`、`logs/`、`*.pid` 互不干扰。特别是 pid 文件名（`merge-bot.pid` vs `relay.pid`）和 jar 名不能一样，否则 `pgrep -f` 和 pid 文件会串。
4. **缺 `.env` 只提示不退出**，沿用模板现有逻辑（真实值也可能通过系统环境变量提供）。

`requeue-dead.sh` 是第四个脚本，但它是补发工具、不参与启停，见 14.16。

### 14.10 合并项目 500 之后云效后台会显示投递失败

**不做会怎样**：运维看到云效后台一片红色，以为系统坏了，去点「重新投递」，结果重复投递。

**做法**：手册里写清楚——走监听服务形态时，云效只看监听服务返回的 200，不会出现这个问题；只有直连形态才会看到失败记录，属于如实反映。重复投递由入队查重（14.14）和合并项目的投递去重挡着；极少数漏过去的，最多群里多一张相同的卡，见 14.12。

### 14.11 老卡片不受影响

**不做会怎样**：担心新逻辑把已经发出去的卡片点坏。

**做法**：按钮值里的字段一直是兼容读取，新增的字段有默认值。旧卡片的四个按钮行为与现在一致。

### 14.12 去重有效期与重试窗口的关系：评估后决定不改（评审修订）

**上一版把这件事定级定高了，这里更正。** 原文档写"任何走到第 6 次重试的消息，去重记录一定已过期，必然多发一张卡"，这个推论是错的。把链路重新走一遍：

1. 合并项目正常处理完会返回 200，监听服务收到就**删文件**，这条消息不会再有后续重试。去重窗口过没过期根本不影响它。
2. 会产生"重复转发"的只有三种情况：转发读超时（合并项目其实处理完了但我们判成失败）、返回 200 但连接被重置、监听服务删文件前崩溃。这些都是**低概率窗口**，不是每次重试都会发生。
3. 一条消息走到第 6 次重试，说明前 5 次都失败了、一次卡都没发出去，第 6 次是它第一次真正发出卡片，**不算重复**。
4. 就算真的重复转发了，14.1 的状态复查还会先查一次云效：请求已被合并或关闭的，直接跳过不发卡；只有仍然待合并的才会多出一张卡。
5. 最终影响是**群里多一张一模一样的审批卡**，刷屏，仅此而已。合并代码不会被执行两次——写操作前面有锁，落笔前还会重查状态。

所以准确的说法是：需要同时满足"某次转发实际成功但被判失败"和"下一次重试落在去重窗口之外"，才会多一张卡。这是低概率、低影响的组合，不是"必然"。

**关于现有 30 分钟是不是太长**：它不是"处理一条消息要多久"的窗口，而是"云效可能隔多久把同一份报文重投一次"的窗口——`IdempotentStore` 的类注释里写的就是这个理由（云效超时排队几分钟后再重推，窗口太短会发两张卡）。而且走监听服务形态时，云效只跟监听服务打交道，重复投递在**入队查重**（14.14）那一层就挡住了，合并项目这 30 分钟主要服务云效直连的形态一。缩短它没有任何收益，反而会让形态一多发卡，因此**保持 30 分钟不动**。

**关于"调成 4 小时、重启还是会清空"**：这个质疑成立。只调有效期不落盘，合并项目一重启照样全清；而落盘去重要在合并项目里再维护一份持久化状态——可监听服务的文件队列本来就是这套系统的持久层，**两个进程各存一份去重状态属于架构冗余**，为了"极低概率多一张卡"不值得。

**结论（Q1 撤销）**：`IdempotentStore` 一行不改，不新增配置项，不做落盘。只在配置与排错手册里记一句残余风险："监听服务误判失败时，群里可能多出一张相同的审批卡，不影响代码合并结果；重复卡片可直接在群里忽略。"

受这条结论影响，5.8、14.6、14.10、B3、P3/P4/P12 里"取决于去重记录是否还在有效期内"的措辞都已统一改掉，不再把去重当成无条件兜底，也不再把它描述成高风险。

### 14.13 首次到达时间必须独立于文件修改时间（评审补的）

`retry/` 的修改时间被设计成"下次该重试的时刻"，是个未来时间。原文档 5.4 却规定超限时"删修改时间最早的一个"，结果是**删掉最快该重试的那一条**，而不是最老进入队列的那一条；从 `retry/` 移进 `dead/` 的文件还带着这个未来时间，导致死信目录的限额清理也删错。

修法见 5.2 / 5.3：文件名里带首次到达毫秒，"谁最老""是否超龄"一律看它；修改时间只负责"到期了没有"；移进 `dead/` 时把修改时间重置为当前时间。一次解决三处排序问题，也让 Q3 定案的"跨队列统一算超龄"直接复用同一个字段，不用再存一份状态。

### 14.14 入队去重要同时查待发和重试两个目录（评审补的）

原文档只说了"编号固化进文件名"，没写入队时怎么判重。`pending/` 里同名文件会互相覆盖，看着像天然去重；但消息一旦失败移进 `retry/{编号}_*_3.json`，云效此时重投同一份报文，`pending/` 里已经没有它了，会再写一份新文件，两条并存、分别处理，发两张卡。

**做法**：写文件前按投递编号扫 `pending/` 和 `retry/`，命中就直接返回 200 不落盘；`dead/` 里的同编号按"已放弃"处理，也直接返回 200，不复活。扫描只比文件名、不读内容，几十个文件开销可忽略。

### 14.15 状态复查的插入位置和验法（评审补的）

判断要插在 `pushCard` 拿到 `MrView` 之后、`commitsFor()` / `webUrlFor()` 之前，状态不是待合并就立刻返回，省掉后面两三次无谓的云效接口调用。webhook 路径走的是 `MrView.of(n)`（不带状态兜底），状态读不到时 `getStatus()` 是空串，正好落到 14.1 的"照常发卡"兜底，两边对得上。

验收要注意：不能用 `action=close` 的报文去测这条判断，现有 `dispatch` 只处理 `open` / `reopen`，close 在状态复查之前就被忽略了，返回 200 但根本没走到新逻辑。必须用 open 动作、但对应请求在云效上已经合并或关闭的报文（见 C6）。

### 14.16 死信目录怎么补发（评审补的，原文档只有一句"手工丢回队列"）

**先把现状说清楚**：死信**不自动重发**。原文档在 5.8 写了"手工补发要改文件名、次数归零"，在 9.3 列了"手册加一节死信补发"，但那一节的具体内容一直没写，也没有任何工具——等于只留了一句口号。而 Q2 定案后，凭据失效会把一批消息成批送进死信，这个问题就躲不过去了。

**定位**：`dead/` 是"人工待办清单"，不是另一个重试队列。它收的是"自动重试已经用尽"或"重试再多次也无用"的消息，再自动重发只会造成无限循环。令牌什么时候换好，机器也判断不了。所以由人在服务器上手工触发一次批量补发。

**为什么必须能批量**：令牌失效期间，每条消息都会 400 进死信，一次故障可能攒几十条。让人一条条改文件名不现实。

**做法一：文件名带原因**（已写进 5.2）。换完令牌后这样筛：

```bash
ls -1 queue/dead/*_auth_*.json
```

**做法二：一个只做一件事的脚本 `requeue-dead.sh`**，接收一个文件名参数，把它放回待发队列：

```bash
./requeue-dead.sh queue/dead/a1b2c3d4-0001_1763604612000_20261120093012_auth.json
```

脚本只做四步：从文件名里解析出编号 → 生成新名字 `{编号}_{当前毫秒}.json`（次数归零、原因标记去掉）→ 移到 `pending/` → 把修改时间设成当前。每处理一个文件打印一行，成功失败都能看见，**不塞"批量模式""按原因过滤""清理"等其它功能**。要批量就自己写 for 循环：

```bash
for f in queue/dead/*_auth_*.json; do ./requeue-dead.sh "$f"; done
```

为什么用脚本而不是加一个 `POST /admin/requeue` 接口：监听服务的 18123 是对云效开放的公网端口，加管理接口就得再配一套鉴权；脚本只在服务器本机跑，没有暴露面，而且 `ls` 加一行循环就能看清补发了什么，排查路径更短。

**补发后的行为**：文件回到 `pending/` 后就是一条全新消息，重新走六次阶梯；发卡前照样会重查云效状态，早已合并或关闭的会被 14.1 拦掉，不会刷废卡。

**保留期**：`dead/` 里的文件保留 7 天（5.4、8.1），过期直接删除并记警告日志。7 天足够人发现故障、换令牌、补发；过期再删也不会让报文（含姓名邮箱）无限期留在磁盘上。手册里要写明"7 天内可补发"。

## 十六、三轮评审结论

### 16.1 第一轮评审改了什么

对照现有代码逐条核实后，纠正了以下几类问题：

**会导致功能直接不工作的（已改进正文）**

| 问题 | 原来怎么写 | 改成 |
|---|---|---|
| 转发头名 | `X-Relay-Delivery` | 必须带 `X-Codeup-Delivery`，否则 `WebhookGuard.deliveryOf()` 取不到编号，每条都 400 进死信（6.2） |
| Content-Type | 写死 `application/json` | 原样透传云效的 Content-Type，否则中文可能乱码（6.2） |
| 400/503 判定 | 按异常类别 | 白名单：只有"重试再多次也没用"判 400，其余一律 503；发卡失败抛的是 `IllegalStateException`，不在云效异常分类里（6.2） |
| 让路阈值 | 50，与待发上限同为 50 | 10，`> 50` 在 50 上限下永远不成立，规则形同虚设（5.6） |
| 超限丢弃 | 删修改时间最早的 | `retry/` 的修改时间是未来时刻，会删错；改按文件名里的首次到达时间（5.2 / 5.3 / 5.4） |
| 入队查重 | 没写 | 必须同时查 `pending/` 和 `retry/`（5.2 / 14.14） |
| 死信补发 | "丢回 pending 即可" | 要重置次数和文件名，否则补发立刻又进死信（5.8） |
| 回滚 | "残留文件不影响运行" | 残留消息会直接丢；先让队列跑空再停，或手工 curl 补发（10.3） |

**文档自相矛盾的（已统一）**

- 云效入口到底返不返 500：4.3 理由 1、6.3 说"保持 200"，P11 说"返 500"，而用户早已确认"5 行返回 500 改"。已统一为**如实返回 500**，4.3 理由 1 改成"两套返回码语义不同"。
- 验收标准与实现打架：A1「2 秒出卡」、A3「3 条 2 秒处理完」与 14.6「一条要几秒」矛盾；A2、B3 说"文件留在 pending"，实际失败会移进 `retry/`；B3 的"最坏多发一张卡"与已修正的 P3 矛盾；C6 用 close 报文测不到状态复查。已逐条改。
- C5 期望返 503，但 7.2 已把 401/403 归为"令牌问题"，重试六次毫无意义。第二轮已定案**返 400 进死信 + 批量补发**（Q2、14.16）。
- 改动清单漏了 `WebhookDispatchService`：`dispatch` 是 `private`、带 7 个注入对象和十几个辅助方法，两个入口要共用必须先抽服务。已补，合并项目合计 480 → 650 行（第三轮又加了 doctor 自检项与测试）。

**第一轮提得过高、第二轮已更正的**

- P3 / P4 / P12：第一轮把"去重有效期 30 分钟 < 重试总长 2 小时 38 分"定成"必然多发卡、中高风险"，**这个推论是错的**。正常处理完返回 200 就删文件、不会有后续重试；走到第 6 次的消息是第一次真正发卡，不算重复；只有"转发实际成功却被判失败"且"下一次重试落在 30 分钟后"才会多一张卡，结果也只是刷屏，不是重复合并。已降级为低风险、**决定不改代码**，详见 14.12。
- 新增 P13（`application.yml` 顶部关于 `.env` 的注释已过时，会误导部署）、P14（`/health` 挂对外端口无鉴权）。

**其他补充**：`YunxiaoException` 实际有六处抛出点，不止两处（7.2）；`doMerge` / `doClose` 的 catch 里已经在 `forget`，统一出口别重复加（7.3）；状态复查的插入位置（14.15）。
