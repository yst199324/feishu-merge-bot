# 云效合并请求 → 飞书卡片 → 一键合并

在飞书群里收到一张卡片，上面写着"谁提交了什么、合到哪个分支"，点「合并」或「拒绝」就直接在云效上执行，不用再打开浏览器找那个合并请求。

卡片底部还有两个按钮：「在云效打开」直接跳浏览器；右边的「复制」点了之后，机器人会把这条合并请求的链接**私聊发给你**——手机上一键就能长按复制，再粘到电脑上接着看（卡片里的文字在手机上是选不中的，长按只会弹出消息菜单）。

这是一个单进程的 Java 服务：接住云效推送的合并请求消息，拼成飞书卡片发到群里，再通过飞书长连接收你点按钮的结果，回头去调云效的合并接口。

**本文档从零开始写**：飞书应用怎么建、权限开哪几个、云效令牌怎么申请、Webhook 怎么配、配完怎么一键自检。照着一步步点就能跑起来。

## 一、它怎么工作

```
① 有人新建合并请求
        ↓
② 云效把这件事推给本服务（代码库 Webhook）
        ↓
③ 本服务调云效接口补全信息（仓库名、分支、最近提交、有没有冲突、评审有没有过）
        ↓
④ 拼成卡片，发到审批群
        ↓
⑤ 你在飞书点「合并」
        ↓
⑥ 飞书通过长连接把"谁点了哪个按钮"推回本服务
        ↓
⑦ 本服务重新查一遍：你是不是群里的人、请求还开着吗、有没有冲突、卡点过了吗
        ↓
⑧ 都过了才弹二次确认，再点一次才真的调云效合并接口
        ↓
⑨ 卡片原地变绿（已合并）或变灰（已拒绝）
```

**第 ⑦ 步是重点**：这个按钮不是绕过评审的后门。点按钮时会把状态重新查一遍，云效的合并接口里还会再拦一次卡点。评审没过、有冲突、请求已关闭，都会被拒绝并告诉你原因。

## 二、三条触发链路，选一条

| 方式 | 需要公网吗 | 延迟 | 说明 |
|---|---|---|---|
| **A. 云效代码库 Webhook**（推荐） | 需要 | 毫秒级 | 报文最完整，卡片信息最全 |
| **B. 定时轮询** | **不需要** | 约 1 分钟 | 服务自己定时去云效问"有没有新的待合并请求" |
| C. 云效流水线调接口 | 需要 | 秒级 | 老方案，拿不到合并请求编号，不推荐 |

没有公网 IP、没有备案域名，就走 B，功能完全一样，只是慢一点。两种不要同时开，否则同一个请求你会收到两张卡。

**飞书那一侧不需要公网。** 服务主动连飞书，按钮点击顺着这条连接推回来，所以不用配置回调地址、不用验签、不用域名备案。公网只是给云效推送用的。

## 四、飞书应用从零创建

这一章不针对本项目，任何"要让机器人往群里发消息、还能点按钮"的需求都是这套流程。**顺序不能乱**，尤其是"开权限 → 发版本"，很多人卡在最后一步。

### 4.1 创建企业自建应用

1. 浏览器打开 [open.feishu.cn](https://open.feishu.cn/)，右上角点「开发者后台」
2. 左侧「创建应用」→「企业自建应用」
3. 填应用名称（比如「合并审批助手」）、描述，随便传个图标 → 「创建」

> **一定是"企业自建应用"**，不是"商店应用"。商店应用要走发布审核，个人用不上。

### 4.2 拿到 App ID 和 App Secret

创建完会自动进入应用详情页。左侧「凭证与基础信息」，这一页有两个值：

| 值 | 长什么样 | 用在哪 |
|---|---|---|
| App ID | `cli_` 开头，比如 `cli_a1b2c3d4e5f6` | 配置项 `feishu.app-id` |
| App Secret | 一串随机字符，点「显示」才看得到 | 配置项 `feishu.app-secret` |

⚠️ **App Secret 等同于密码**，不要发到群里、不要提交进 Git。它写在项目根目录的 `.env` 里（不进仓库），`application.yml` 里只有一个中文占位值。

### 4.3 开通权限（最关键的一步）

左侧「权限管理」，页面上方有搜索框。**搜中文名比搜标识好找。**

本项目需要下面 4 个，缺任何一个都会有一个功能用不了：

| 中文名 | 权限标识 | 用来干什么 | 不开会怎样 |
|---|---|---|---|
| 查看群成员 | `im:chat.members:read` | 判断点按钮的人是不是审批群里的人 | 群里**所有人**点按钮都提示「没有合并权限」 |
| 获取群组信息 | `im:chat:readonly` | 查机器人被拉进了哪些群，用来拿群 ID | 拿不到 `chat-id`，配置填不出来 |
| 以机器人身份发消息 | `im:message:send_as_bot` | 往群里发卡片 | 发卡片直接报权限不足 |
| 获取通讯录基本信息 | `contact:contact.base:readonly` | 把操作人从 `ou_xxx` 显示成真实姓名 | 卡片上显示「未知用户（末 6 位）」，**不影响合并** |

操作方式：搜索框输入中文名 → 勾上这一行 → 点「批量开通」。

**关于通讯录那条，有个坑要单独说**：飞书给的是下面四条，**开任意一条**就够：

```
contact:contact.base:readonly      ← 推荐这个，就是本项目在用的
contact:contact.access_as_app
contact:contact.readonly
contact:contact.readonly_as_app
```

网上不少教程写的是 `contact:user.base:readonly`，那是**错的**，开了没用。如果日志里看到：

```
One of the following scopes is required:
[contact:contact.base:readonly, contact:contact.access_as_app, ...]
```

说明就是缺通讯录权限，按上面四条里选一条开。

> 报错原文里通常自带一个带 app-id 的直达链接，点开就是你的应用权限页，比翻菜单快。

### 4.4 开启机器人能力

左侧「添加应用能力」→ 找到「机器人」→「添加」。

不开这一步，应用只是个空壳，不会被当成机器人，也进不了群。

### 4.5 设置可用范围

左侧「版本管理与发布」→ 页面里有个「可用范围」。

- 想省事：选「全部员工」
- 通讯录权限和可用范围是两回事：**人不在可用范围，就算开了通讯录权限也查不到名字**（报 41050）

本项目建议选「全部员工」，避免"某些人点了按钮显示未知用户"。

### 4.6 创建版本并发布

⚠️ **加了权限不发版，等于没加。** 这是整个流程里最容易漏、也最让人抓狂的一步：权限页面显示"已开通"，接口还是报 99991672。

1. 左侧「版本管理与发布」→「创建版本」
2. 填版本号（`1.0.0`）、更新说明（随便写，比如"首次发布"）
3. 保存 →「申请发布」
4. 如果你是管理员，审核页点通过；不是的话找管理员审

**以后每次改权限、改机器人配置，都要重新发一次版本**，否则不生效。

### 4.7 把机器人拉进审批群

打开那个群 → 右上角「设置」（齿轮）→「群机器人」→「添加机器人」→ 搜索你的应用名 → 添加。

加完**先别关这个设置页**，往下拉到最底部，有一行「会话 ID」，`oc_` 开头的一长串字符，点一下就能复制。这个就是配置里要填的 `feishu.chat-id`。

抄的时候注意三点：

- 要的是「会话 ID」（`oc_` 开头），不是「群号」（纯数字），两个长得像但填错了发不出卡片；
- 有的版本把它收在「关于本群」里，展开就能看到；
- 实在找不到，等第 4 步服务起来后调 `/test/chats`，返回列表里对着群名抄。但那条路要先让机器人进群，所以还是先按上面的步骤加机器人。

不加进群，发卡片会报：

```
230002 Bot/User can NOT be out of the chat
```

这一步立即生效，不用重启服务。

### 4.8 事件订阅：选「长连接」

**这一步决定"点按钮有没有反应"。**

左侧「事件与回调」→ 订阅方式选 **「使用长连接接收事件」**（有的版本叫「长连接」）。

选它的好处：

- 不用填任何 URL
- 不用公网 IP、不用域名、不用备案
- 不用处理验签和重放

选「请求地址」（Webhook 方式）也能用，但你就得给飞书提供一个公网 HTTPS 地址，还要自己做验签——本项目没走这条路。

> 配完之后服务启动时日志会出现「正在连接飞书长连接...」和「飞书长连接已建立」。只有后者出现，按钮才是活的。

### 4.9 常见错误码对照表

配的过程中大概率会碰到这几个，先记住长什么样：

| 错误码 | 含义 | 去哪改 |
|---|---|---|
| `99991672` | 应用**没有开通**某个权限，或开了**没发版** | 权限管理里开对应权限 → 版本管理与发布里发版 |
| `41050` | 这个人**不在应用可用范围** | 版本管理与发布 → 可用范围 → 加上他或选全部员工 |
| `230002` | **机器人不在这个群里** | 群设置 → 群机器人 → 添加机器人 |
| `10003` | 参数不对（app-id 写错、多空格等） | 核对 `feishu.app-id` |
| `10014` | App Secret 不对 | 重新复制 `feishu.app-secret` |
| `1000040350` | 同一应用的**长连接数超限**（上限 50） | 查有没有别的进程连着同一个应用 |

## 五、云效侧从零配置

### 5.1 申请个人访问令牌

1. 打开 [codeup.aliyun.com](https://codeup.aliyun.com/)，右上角头像 →「个人设置」
2. 左侧「个人访问令牌」→「新建令牌」
3. 填名称（比如 `合并机器人`）、**到期时间选长一点**（默认只有 7 天，到期后服务会突然全部报 401）
4. 勾权限：

| 权限 | 具体项 | 用来干什么 |
|---|---|---|
| 代码管理 → 代码仓库 | **只读** | 查仓库名、查仓库编号 |
| 代码管理 → 合并请求 | **读 + 写** | 查合并请求状态、执行合并/关闭 |
| 代码管理 → 代码比较 | **只读**（可选） | 只有想让卡片列出"全部提交"时才需要（`use-payload-commit: false`）。默认只显示最近一次提交，不勾也行 |

5. 创建后**立刻复制**令牌值（`pt-` 开头），页面关掉就看不到了

> **强烈建议单独建一个"合并机器人"账号来生成令牌**，别用你自己的。否则云效的审计日志里，所有由机器人执行的合并都会记成你本人操作，以后追责分不清。
>
> 令牌权限可以事后编辑，**改完令牌值不变**，不用改配置也不用重启服务。

如果日志报 `403 Current token has no permission to api.`，就是这里少勾了权限，**不是账号没权限**。

### 5.2 拿组织 ID

打开云效任意页面，看地址栏：

```
https://codeup.aliyun.com/607f9fbe0000000000000/组名/仓库名
                        └────── 这一段就是组织 ID ──────┘
```

填进 `yunxiao.org-id`。

**不能留空**：留空会走另一套接口路径（Region 版），用 `codeup.aliyun.com` 的组织会查不到任何数据，表现为"令牌明明是对的，但什么都查不到"。

### 5.3 拿仓库 ID

新版云效页面的地址栏里**已经不带仓库 ID** 了（形如 `/xxx/组名/仓库名/changes/128`），所以只能反查：

服务起来后调：

```bash
curl "127.0.0.1:8081/test/repos?name=仓库名"
```

返回里的 `repoId` 就是要的值。

另一种办法：云效 Webhook 的投递记录里能看到 `project.id`。

这个值用在两个地方：轮询配置 `poll.repo-ids`，以及流水线映射 `yunxiao.repos`。**走代码库 Webhook 时不需要配它。**

### 5.4 新建 Webhook

仓库页面 →「设置」→「Webhooks」→「新建 Webhook」：

| 项 | 填什么 | 说明 |
|---|---|---|
| 类型 | **普通 Webhook** | ⚠️ 不要选「飞书机器人通知」——那个是云效自己往群里发消息，绕过了本服务，卡片上的按钮出不来 |
| URL | `http://你的公网IP:18123/webhook/yunxiao` | 端口按你实际部署的填。**不能填 127.0.0.1** |
| Secret Token | 和 `yunxiao.webhook-token` **完全一致** | 一个字符不一致就全被拒（403） |
| 触发事件 | **只勾「合并请求事件」** | 把「推送事件」取消。勾了推送事件不会出错，只是日志里多一堆"忽略"，容易看花眼 |

配完点一下云效的「测试」按钮，服务端日志应该出现：

```
忽略非合并请求事件: object_kind=push
```

**这是正常的**——测试按钮发的是推送事件，本来就不该发卡。看到"忽略"两个字，说明**请求已经到了服务里**，链路是通的。

### 5.5 端口必须放行

这一步最容易卡住，而且症状很有迷惑性。

**云效后台看到的只是"投递失败"，很难猜到是防火墙。** 判断方法看耗时：

| 云效投递记录 | 含义 |
|---|---|
| 红 ❌，耗时**十几毫秒** | 端口被防火墙拒绝，TCP 连接直接被掐，包没进程序 |
| 红 ❌，耗时**几秒到 30 秒** | 连接超时，包被中间设备丢了（安全组、运营商） |
| 绿 ✅ 200 | 请求到了服务，接着看 `/test/last-webhook` |

**一句话：快失败=被拒，慢失败=不通。**

放行三步：

```bash
# 1. 确认服务监听所有网卡（出现 127.0.0.1:18123 就是只有本机能连）
ss -lntp | grep 18123

# 2. 系统防火墙（CentOS/RHEL）
firewall-cmd --add-port=18123/tcp --permanent
firewall-cmd --reload
firewall-cmd --list-ports

# Ubuntu 用 ufw：
# ufw allow 18123/tcp

# 3. 云主机控制台的「安全组」也要加入站规则（TCP 18123）
```

要做来源白名单的话，得把云效的两个出口 IP 一起加进去（具体值在云效「代码库设置 → Webhooks」页面的说明里列着），否则云效的请求会被挡在外面。

**验证一定要用外部网络**：手机切 4G，浏览器打开

```
http://你的公网IP:18123/webhook/yunxiao
```

返回 `405 Method Not Allowed` 就是通了（这个地址只收 POST，405 说明请求已经打到程序里）。用公司 WiFi 或同网段机器测都可能走内网直连，测了不算。

## 六、四个步骤跑起来

### 第 1 步：拿代码

```bash
git clone https://github.com/yst199324/feishu-merge-bot.git
cd feishu-merge-bot
```

### 第 2 步：填配置

真实值写在项目根目录的 `.env` 里。**不要改 `src/main/resources/application.yml`** —— 那份是进仓库的模板，里面只有占位值。

```bash
cp .env.example .env
```

然后编辑 `.env`，**必填的只有这 6 项**：

| 变量名 | 填什么 | 从哪拿 |
|---|---|---|
| `FEISHU_APP_ID` | `cli_` 开头 | [4.2](#42-拿到-app-id-和-app-secret) |
| `FEISHU_APP_SECRET` | 一串随机字符 | [4.2](#42-拿到-app-id-和-app-secret) |
| `FEISHU_CHAT_ID` | 审批群 ID，`oc_` 开头 | [4.7](#47-把机器人拉进审批群) 群设置页拉到最底部，抄「会话 ID」 |
| `YUNXIAO_TOKEN` | `pt-` 开头 | [5.1](#51-申请个人访问令牌) |
| `YUNXIAO_ORG_ID` | 组织 ID | [5.2](#52-拿组织-id) |
| `YUNXIAO_WEBHOOK_TOKEN` | 自己定一个随机字符串 | 比如 `mrb-store-2026-abc123`，之后云效那边填同一个 |

没写进 `.env` 的项会回落到 `application.yml` 里的默认值。必填项还留着占位值时，服务启动会直接报 `配置项 [xxx] 未填写` 并退出 —— 不是 bug，是故意的，防止“看起来在跑、其实调不通”。

`.env` 已被 `.gitignore` 排除，不会推到 GitHub。**服务器上也用同一套**：jar 同级放一份这台服务器自己的 `.env`，`application.yml` 只放结构、可以整份覆盖（见第九章）。

#### `.env` 和真正的环境变量，用哪个？

两个都能用，而且**不冲突**。这几项配置的来源是有优先级的，从高到低：

| 顺序 | 来源 | 举例 |
|---|---|---|
| 1 | 启动参数 | `java -jar x.jar --feishu.app-id=cli_xxx` |
| 2 | JVM 参数 | `-Dfeishu.app-id=cli_xxx` |
| 3 | **操作系统环境变量** | `export FEISHU_APP_ID=cli_xxx` |
| 4 | jar 外的 `application.yml` | 第九章服务器那份 |
| 5 | `.env` | 本地这份 |
| 6 | jar 内 `application.yml` 的默认值 | 仓库里这份，只有占位值 |

排在上面的赢。所以你在服务器上 `export` 了某个值，它会盖掉 `.env` 里的，一行代码都不用改。

一点区别值得知道：**`.env` 读进来的是 Spring 的配置项，不是真正的环境变量**。代码里 `System.getenv("FEISHU_APP_ID")` 拿不到它。本项目没有这种调用（全是 `@ConfigurationProperties` 读配置），所以两种方式效果完全一样。

为什么不干脆统一用环境变量？因为 IDEA 里没法从文件自动注入环境变量——只能在 Run Configuration 里手敲（或装 `EnvFile` 插件），而 macOS 上从 Dock 启动的 IDEA 根本不继承终端的环境变量。`.env` 文件方案反而是一个文件三个平台通吃。

**但别让同一个 `.env` 同时被 Spring 和 shell 读。** 两者语法不完全兼容，比如 `TOKEN=abc#123` 在 Spring 眼里是 `abc#123`，在 shell 里 `#` 后面算注释、只剩 `abc`。混用会出现「本地好好的、服务器读到半截」，极难查。要么全走 Spring（推荐），要么全走 shell `source`。

几个值得知道的默认值（这些不敏感，留在 yml 里就行）：

- `feishu.allow-group-members: true` —— **审批群里的人都能点按钮**，加人减人自动生效，不用维护名单（推荐就用这个）
- `TEST_ENDPOINTS`（写在 `.env` 里）—— 调试接口 `/test/*` 的开关，本地默认 `true`。**服务器上必须在 `.env` 里写 `false`**，否则谁都调得动它
- `mergebot.log-webhook-raw: true` —— 把云效推来的报文原文打进日志，排错全靠它

两条容易踩的：

1. **`yunxiao.org-id` 不能留空。** 留空会走另一套接口路径，用 `codeup.aliyun.com` 的组织会查不到数据。
2. **`yunxiao.webhook-token` 不能是空、也不能留着样例值。** 走 Webhook 触发时这一项必须填，否则 `/webhook/yunxiao` 会拒绝所有请求（安全默认值）。只有走轮询时才可以留空——但两个都没配，服务启动时直接报"没有任何触发方式"然后退出。

### 第 3 步：编译

```bash
mvn clean package
```

产物固定叫 `target/merge-bot.jar`（`pom.xml` 里锁了名字，文档里的命令不用跟着版本号改）。

**这一步会顺带跑完所有单元测试**，现在一共 71 个用例，全绿才算通过（数量会随迭代增加，看总数不为 0、失败为 0 就行）。只想跑测试、不打包：

```bash
mvn test
```

### 第 4 步：启动

```bash

```

看到这两行就成功了：

```
配置校验通过，开始连接飞书
Started MergeBotApplication in xxx seconds
```


## 七、一键自检：一条命令查完所有配置

前面那些配置，漏一项就要花半小时找原因。所以做了一个接口，**把所有依赖一次查完，每项都告诉你"怎么修"**。

### 7.1 怎么用

**前提：`TEST_ENDPOINTS` 必须是 `true`。** 本地默认开着；服务器上默认关（`.env` 里写的是 `false`），关着时访问会得到 404 —— 见 [9.3](#93-日常三条命令) 里"验收时怎么临时打开"。

浏览器直接打开，不用传任何参数：

```
http://127.0.0.1:8081/test/doctor
```

服务器上：

```
http://你的公网IP:18123/test/doctor
```

两个可选参数：

| 参数 | 作用 | 默认 |
|---|---|---|
| `?card=false` | 不发测试卡片 | 默认**会**发一张到群里 |
| `?format=json` | 返回结构化数据，给脚本用 | 默认纯文本，人看 |

```bash
# 纯文本（默认）
curl 127.0.0.1:8081/test/doctor

# 只想看结果、不想打扰群里
curl "127.0.0.1:8081/test/doctor?card=false"

# 给脚本用
curl "127.0.0.1:8081/test/doctor?format=json"
```

**检测全部是只读操作**，唯一的副作用是那张自检卡片（`card=false` 可以关掉）。可以反复跑，跑十次的结果应该一样。

### 7.2 它查什么：20 项

| # | 检测项 | 查的是什么 | 报错说明什么 |
|---|---|---|---|
| **配置** | | | |
| 01 | 必填配置项 | 令牌、app-id、app-secret、chat-id 是否为空或还是样例值 | 有项没填，或配置改在了别的地方没生效。**模板里的中文占位值（`pt-你的令牌`）算没填** |
| 02 | 触发方式 | Webhook 和轮询至少开一个；两个都开也会提示 | 一个都没开 → 永远不会发卡片；都开 → 同一个请求收到两张卡 |
| 03 | 轮询配置 | 轮询开了，`repo-ids` 有没有填 | 轮询线程空转，扫不到任何仓库 |
| 04 | 谁能点按钮 | 白名单和「群成员可点」的组合 | 两个都关掉 → 任何人点都提示没权限 |
| 05 | 云效组织 ID | `org-id` 是否填写 | 留空会走 Region 路径，查不到数据 |
| **云效** | | | |
| 06 | 令牌有效、能读代码库 | 真调一次「列仓库」接口 | `401`=令牌过期；`403`=令牌少权限；超时=网络 |
| 07 | 能读合并请求 | 对配置的仓库查一次待合并列表 | 缺「合并请求 读」权限，或仓库编号写错 |
| 08 | 仓库编号有效 | 逐个直接查仓库详情（**不走缓存**） | 编号写错，或令牌看不到这个仓库 |
| 09 | 合并 / 关闭的写权限 | **验不了，标"待确认"** | 只有真合一次才知道 |
| **飞书** | | | |
| 10 | 应用凭证、能列群 | 用 app-id/secret 拿令牌并列群 | `10014`=secret 错；`99991672`=缺群组信息权限 |
| 11 | 审批群可访问 | 直接查这个 chat-id | `230002`=机器人不在群；`99991672`=缺权限 |
| 12 | 能查群成员 | 拉一次群成员列表，报人数 | 缺「查看群成员」，**所有人都点不动按钮** |
| 13 | 能换出人名 | 自动从群里挑一个真人去查姓名 | 缺通讯录权限（只是显示成"未知用户"，不影响合并） |
| 14 | 长连接（按钮回调） | 长连接是否已建立 | 卡片能发、点按钮没反应，就是这一项 |
| 15 | 能发消息 | **真发一张自检卡片到群** | 发不出去说明权限或群不对 |
| **运行环境** | | | |
| 16 | 服务监听地址 | 只监听 `127.0.0.1` 还是所有网卡 | 只听本机时，云效从公网打不进来 |
| 17 | 运行环境 | JDK 版本、安装路径 | 排查"是不是跑错 java" |
| 18 | 配置文件来源 | **和 jar 同级**有没有 `application.yml` | 有就是 start.sh 加载的那份；没有说明改外面配置不生效 |
| 19 | 最近一次 Webhook | 服务起来后有没有真收到过推送 | 从没收到过 → 云效没配好，或端口没放行 |
| 20 | 排错接口开关 | `test-endpoints` 是不是开着 | 验收完要关掉 |

### 7.3 怎么读结果

每项有四种状态：

| 状态 | 意思 | 要做什么 |
|---|---|---|
| `[通过]` | 验证过了 | 不用管 |
| `[待确认]` | 要么验不了，要么缺了不影响主流程 | 看「怎么修」那行，自己判断要不要处理 |
| `[需要修]` | 不改就用不了 | 必须处理 |
| `[跳过]` | 前面某一项没过，这项没测 | 先修上一项，再跑一次 |

输出长这样（真实格式，内容是示例）：

```
======== 合并审批机器人 · 自检 ========
2026-11-19 13:20:41    共 20 项：通过 14 · 待确认 3 · 需要修 2 · 跳过 1

最先要修：11 审批群可访问

【一、配置文件】
[通过] 01 必填配置项
         详情：云效令牌 ✓  飞书 app-id ✓  飞书 app-secret ✓  审批群 chat-id ✓
[通过] 02 触发方式
         详情：云效 Webhook（需要公网能访问到本服务）
[跳过] 03 轮询配置
         详情：轮询没开，走 Webhook，这项不用管
...

【三、飞书】
[需要修] 11 审批群可访问
         详情：230002：机器人不在这个群里
         怎么修：打开那个群 → 右上角设置 → 群机器人 → 添加机器人 → 选你这个应用。加完立即生效，不用重启
...

--------------------------------------------------
两点说明：
 · 「合并 / 关闭」写权限没法自动验证，只有真合一次才知道。
 · 公网能不能访问不在这里测：服务从自己机器访问自己的公网地址会走内网，
   防火墙没放行也照样通，测了等于没测。真要验：手机切 4G 打开
   http://公网IP:端口/webhook/yunxiao ，返回 405 就是通的。
```

**只有出现「需要修」时，第一行下面才会写「最先要修：xx」，直接告诉你先动哪一个。** 一个「需要修」都没有时，那句会变成「没有必须修的项」，不会把「待确认」的项顶上来凑数——写权限那一项永远是待确认，如果把它当待办，每次跑都会看到一条修不了的事。

### 7.4 它故意不做的两件事

**① 不测公网可达性。**

想在服务端验证"云效能打进来"，只能让服务去请求自己的公网 IP。但服务器访问自己的公网 IP 走的是内网回环，**安全组没放行也照样通**——那样测出来的"通过"是假的，比不测更糟。

所以这一项只做两件事：显示"最近一次收到 webhook 是几点"（真收到过就是通的），以及给出人工验证方法（[5.5](#55-端口必须放行)）。

**② 不给写权限打绿勾。**

令牌有没有合并权限，只有真合一次才知道。不会为了凑一个"全部通过"去调合并接口。这一项固定标「待确认」，并提示你拿测试仓库实测一次。

### 7.5 什么时候还该跑一次

不只是一次性验收。下面这些时候都值得跑：

- 换了服务器、换了部署目录
- 云效令牌重新生成过（默认 7 天过期，很容易忘）
- 飞书后台改过权限、发过新版本
- 群里突然所有人都点不动按钮
- 卡片能收到，但点按钮没反应

## 八、手动逐条验证（自检之外）

自检能覆盖 90%，剩下这些只能手动看：

```bash
# 服务活着吗
curl 127.0.0.1:8081/test/whoami

# 飞书配置对吗，群里能找到吗
curl 127.0.0.1:8081/test/chats

# 云效令牌能用吗
curl 127.0.0.1:8081/test/repos

# 发一张演示卡片（不看真实数据，只看样式）
curl 127.0.0.1:8081/test/card

# 发一张真实数据的卡片（换成你的仓库 ID 和合并请求编号）
curl "127.0.0.1:8081/test/card?repo=你的仓库ID&mr=合并请求编号"
```

> 最后一条的 URL **必须加双引号**，否则 `&` 会被 shell 当成后台执行符吃掉，只传了前半个参数。

卡片到了群里之后，**在卡片上点一下按钮**，服务端日志会出现「收到卡片回调」——出现这行，说明长连接和按钮回调也通了。

云效推送进来之后，随时可以查最近一条报文的处理结果：

```bash
curl 127.0.0.1:8081/test/last-webhook
```

它会告诉你这份报文被怎么处理了（发了卡 / 被忽略 / 哪一步失败），以及报文原文和请求头。

## 九、部署到服务器

### 9.1 放什么

```
/你的目录/mergebot/
├── merge-bot.jar        # mvn package 的产物
├── application.yml      # 直接用 src/main/resources/application.yml 覆盖过来
├── .env                 # 本机专属的真实值，从 deploy/.env.example 复制
├── start.sh
├── stop.sh
└── restart.sh
```

关键设计：**`application.yml` 只描述结构，不含任何真实值**。里面的凭据、端口、调试开关全是 `${KEY:占位}` 形式，真实值统一从同目录的 `.env` 读。

好处有两个：

1. 本地改完 `application.yml`（加配置、改注释），**整份覆盖到服务器就行**，不会冲掉服务器上的凭据
2. 服务器和本地只有 `.env` 不一样，那份永远不用动

`deploy/application.yml`、`deploy/.env`、`deploy/*.jar` 都在 `.gitignore` 里，都是本机或服务器上的拷贝件。仓库里给模板的只有一份：`deploy/.env.example`。

`application.yml` **没有模板文件**，直接用 `src/main/resources/application.yml` 复制过去就行——它本来就只有结构、不含真实值。也**不要在服务器那份里写真实凭据**：外置 yml 的优先级高于 `.env`，一旦写成本地字面值，下次覆盖时又会把服务器上的值冲掉，回到"每次手改"的老问题。

### 9.2 三步配好

**① 放配置文件：不用改任何值**

```bash
cp src/main/resources/application.yml /你的目录/mergebot/application.yml
```

**② 建 .env：填这台服务器自己的值**

```bash
cp deploy/.env.example /你的目录/mergebot/.env
vi /你的目录/mergebot/.env
```

六项凭据（飞书 app-id/secret、群 ID、云效 token、组织 ID、webhook-token）的获取方式见第四章、第五章。另外两项是服务器专属的：

| 变量 | 填什么 |
|---|---|
| `SERVER_PORT` | 服务监听端口，比如 `18123`。填完云效 Webhook 的 URL 要对应成 `http://你的公网IP:18123/webhook/yunxiao` |
| `TEST_ENDPOINTS` | **必须是 `false`**。模板里已经写好了，别删 |

> `TEST_ENDPOINTS` 这一项最容易漏。它的默认值是 `true`（本地调试方便），服务器上不显式关掉，`/test/*` 就在公网上敞着，谁都能调它往审批群发卡片。

**③ 改 start.sh 里的 JDK 路径**

`deploy/start.sh` 第 31 行写死了：

```bash
JAVA_BIN="/root/jdk/jdk-17.0.17/bin/java"
```

**换成你服务器上真实的 java 路径**，否则会报"找不到 JDK"。用 JDK 8 就把下面那行注释掉、这行改掉。

### 9.3 日常三条命令

```bash
cd /你的目录/mergebot
chmod +x start.sh stop.sh restart.sh   # 第一次要加执行权限

./start.sh      # 启动
./stop.sh       # 停止
./restart.sh    # 重启（改完 jar 或配置都用它）
```

`start.sh` 会做这些检查，不满足直接报错退出，不会稀里糊涂启动：JDK 在不在、jar 在不在、配置在不在、是不是已经在跑了。

日志在 `logs/` 下：

```bash
tail -f logs/merge-bot-info.log      # 业务日志，日常看这个
tail -f logs/merge-bot-error.log     # 只看报错
tail -f logs/console.log             # 启动阶段的输出（logback 生效前的报错只在这里）
tail -f logs/merge-bot-audit.log     # 谁在什么时候点了什么、结果如何，保留一年
```

部署完第一件事：跑一次自检。但先注意 —— `.env` 里 `TEST_ENDPOINTS` 是 `false`（公网安全默认值），这时访问会返回 404，不是功能坏了。

```bash
# 1. 临时打开调试接口。改 .env，不要改 application.yml
#    （改 yml 的话，下次整份覆盖回来又会被重置）
sed -i 's/^TEST_ENDPOINTS=.*/TEST_ENDPOINTS=true/' .env
./restart.sh

# 2. 跑自检（card=false 表示不往群里发测试卡片，验收阶段建议关掉）
curl "127.0.0.1:18123/test/doctor?card=false"

# 3. 验完立刻改回去，再重启一次
sed -i 's/^TEST_ENDPOINTS=.*/TEST_ENDPOINTS=false/' .env
./restart.sh
```

> 不想用 sed 就 `vi .env` 手动改这一行，效果一样。
>
> **第 3 步别忘。** 这个接口能让机器人往群里发卡片、能读出群 ID 和仓库列表，留在公网等于一个没上锁的控制台。

## 十、没有公网就开轮询

把配置改成：

```yml
mergebot:
  poll:
    enabled: true
    interval-ms: 60000
    repo-ids:
      - "1234567"
    target-branches:
      - "prod"        # 只关心合到 prod 的，留空 = 全部
    repo-names:
      "1234567": store-web-new
```

仓库 ID 从哪来：[5.3](#53-拿仓库-id)。

服务启动 15 秒后扫第一轮，之后每分钟一轮。功能完全一样，只是延迟一分钟。

> **轮询配置不在 `.env` 里，属于 `application.yml` 的结构部分。** 所以服务器开了轮询之后，下次把仓库里那份 `application.yml` 整份覆盖上去，`enabled: true` 会被重置回 `false`。
>
> 两个办法，选一个：
>
> 1. **本地这份 yml 也改成 `enabled: true`**（连 `repo-ids` 一起），以后覆盖过去就是对的 —— 推荐，一劳永逸
> 2. 覆盖完再手动改回 `true` 并重启 —— 容易忘，忘了就是"服务在跑但一张卡都不发"，很难查

## 十一、配置项完整说明

按用途分组。没列出的保持默认就好。

### 服务本身

| 配置项 | 默认 | 说明 |
|---|---|---|
| `server.port` | 8081 | 监听端口，云效 Webhook 的 URL 用它 |
| `server.address` | 空（所有网卡） | 填 `127.0.0.1` 后只有本机能连，适合前面挂 Nginx 反代 |
| `TEST_ENDPOINTS`（写在 .env） | true | `/test/*` 调试接口和自检接口的开关，**服务器上必须在 .env 里写 false** |
| `mergebot.log-webhook-raw` | true | 是否把报文原文打进日志 |
| `mergebot.use-payload-commit` | true | 优先用报文里的最近提交，省一次接口调用。改 false 会列出全部提交，但令牌要多勾一项「代码比较 → 只读」 |

### 飞书

| 配置项 | 默认 | 说明 |
|---|---|---|
| `feishu.app-id` | 必填 | 应用 ID |
| `feishu.app-secret` | 必填 | 应用密钥 |
| `feishu.chat-id` | 必填 | 审批群 ID，`oc_` 开头。从群设置页拉到最底部抄「会话 ID」 |
| `feishu.allow-group-members` | true | 是否允许审批群成员点按钮 |
| `feishu.allowed-open-ids` | 空 | 固定白名单，和上一条是"或"关系。一般不用填 |
| `feishu.group-member-cache-seconds` | 300 | 群成员判断结果缓存多久。刚被移出群的人最迟这么久之后点不动，刚进群的人立刻能点 |

> `open_id` 是按应用算的：同一个人在别的飞书应用里的 open_id 跟这里不一样。写错了会一直提示没权限。想看自己的 open_id，在群里随便点一次卡片，提示气泡里会写。

### 云效

| 配置项 | 默认 | 说明 |
|---|---|---|
| `yunxiao.token` | 必填 | 个人访问令牌，`pt-` 开头 |

## 十三、出问题了看哪里

**先跑一次自检**，九成的问题它会直接指出来：

```bash
curl "127.0.0.1:8081/test/doctor?card=false"
```

自检没覆盖的，按这个顺序看日志：

```bash
tail -f logs/merge-bot-info.log
```

| 现象 | 先查什么 |
|---|---|
| 云效点了测试按钮，日志什么都没有 | 端口没放行，或者云效那边 URL 填错。手机切 4G 开 `http://公网IP:端口/webhook/yunxiao`，405 才算通 |
| 日志有"忽略非合并请求事件" | 正常，测试按钮发的是推送事件，不发卡 |
| 日志有"没带 X-Codeup-Delivery，本次丢弃" | 请求头被中间代理过滤了。查 Nginx 的 `proxy_set_header` 有没有白名单把未知头吃掉 |
| 群里收不到卡片 | ①`feishu.chat-id` 对不对（群设置页拉到最底部抄「会话 ID」，或 `/test/chats` 查）②机器人进群没 ③权限发版没 |
| 卡片能收到，点按钮没反应 | 长连接没连上。自检第 14 项会直接说；日志搜「飞书长连接已建立」 |
| 点按钮提示"没有合并权限" | `im:chat.members:read` 没开，或者开了没发版 |
| 点「复制」提示私聊发送失败 | 机器人发不了这个人的单聊：①开发者后台 → 应用可用范围里有没有这个人 ②`im:message:send_as_bot` 有没有发版。临时办法是先点「在云效打开」，从浏览器地址栏复制 |
| 卡片上操作人显示"未知用户（末 6 位）" | 缺通讯录权限，开 `contact:contact.base:readonly` |
| 报 `403 Current token has no permission to api` | 云效令牌少勾权限，不是账号没权限。改令牌权限即可，令牌值不变、不用重启 |
| 同一个请求重开两次，只收到一张卡 | 老版本的问题，已修。现在按云效的投递编号去重，每次重开都会发新卡 |
| 合并报"云效令牌失效或权限不足" | 令牌被删、权限被改、或账号停用。服务会往群里发一条带处理步骤的提醒 |

更细的排错路径（每一项都对应一次真实踩坑）在配套手册里：`云效合并请求飞书审批机器人（配置与排错手册）.md`。

## 十四、几条要知道的边界

- **去重记录和"当前有效卡片"都存在内存里。** 服务重启就清空，所以重启期间云效重推的报文可能重复发卡，历史上发过的卡也不会再自动更新。
- **每次"关闭后重开"都会发一张新卡**，老卡不会失效。点老卡上的按钮仍然会执行（只要那个请求还开着），因为校验看的是请求的真实状态，不是卡片的新旧。
- **两个触发入口不要同时开**（Webhook 和轮询），同一个请求会收到两张卡。
- **debug 接口 `/test/*` 在公网必须关掉。** 它能让机器人往群里发卡片、能查云效数据，等于一个没有门锁的控制台。自检接口也在这个开关下面。
- **云效个人访问令牌默认 7 天过期。** 到期那天服务会突然全部报 401，卡片也发不出来。要么创建时把有效期选长，要么把"换令牌 + 重启"写进日历。
